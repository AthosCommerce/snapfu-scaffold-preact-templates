# AGENTS.md

## Project

An Athos Commerce **Snap Templates** integration for one storefront, generated by snapfu from `snapfu-scaffold-preact-templates`. It ships one bundle that renders search, autocomplete and recommendations on the client's site.

Snap Templates is configuration-first. The whole integration is one `SnapTemplates` config in `src/index.tsx`, built on the themes and components in `@athoscommerce/snap-preact`. In locked mode the only custom Preact code it accepts is result and badge components. That is deliberate, not a limitation to work around.

Docs: [Config](https://athoscommerce.github.io/snap/templates-config) · [Theming](https://athoscommerce.github.io/snap/templates-theming) · [How Tos](https://athoscommerce.github.io/snap/templates-how-tos). Look up props, defaults and config keys there, or in the installed package's types. Don't rely on memory: legal props change between releases.

## Stack

Preact 10, not React: the JSX pragma is `h` and hooks come from `preact/hooks`. MobX state, TypeScript compiled by `ts-loader` with `strict: false`, Emotion object styles through the theme style script. webpack builds two bundles, `modern` and `universal` (for legacy browsers).

## Layout

```
src/
├── index.tsx          the SnapTemplates config, and nothing else
├── styles.ts          globalStyles, the theme style script (composes src/styles/* once split)
├── styles/            optional: one style module per area (toolbar.ts, facets.ts, ...)
├── components/        custom result and badge components (Result.tsx is the starter)

└── universal.ts       legacy-browser entry: loads polyfills, then imports index

```

**Scaffold-managed files** open with `DO NOT EDIT - THIS FILE CAN/WILL BE REPLACED!!!`: `src/types.d.ts`, `eslint.config.js` and the `webpack.*.js` files. `snapfu patch` overwrites them and local edits are lost without warning. If one seems to need a change, raise it as a scaffold change instead.

## Stay locked

Locked mode is the default and the goal: `validateTemplatesConfig`, a config typed as `SnapTemplatesConfig`, and no `unlocked` key. In locked mode:

- theme overrides accept only each component's `*TemplatesLegalProps`
- `components` registers only `result` and `badge` components
- `plugins` covers the built-in `common` and platform plugins

That narrow surface is what lets `snapfu patch` upgrade the integration cleanly, because the SDK still owns everything it renders.

**Never unlock without explicit approval from the engineer who owns the integration.** Unlocking takes two changes together, `validateTemplatesConfigUnlocked` and `unlocked: true`. One without the other doesn't unlock. All it adds is `customComponent` on non-result components and `plugins.custom`. `result` never accepts `customComponent`, locked or unlocked: use `resultComponent` or `theme.globalResultComponent`.

Before asking to unlock, work down this list and stop at the first step that works:

1. A legal prop on the Snap component, set in `theme.overrides` (per breakpoint if needed).
2. Text and labels: `translations`.
3. Appearance: the style script. See [Styling](#styling).
4. Arrangement: layout strings and toolbar or sidebar module arrays in `theme.overrides`.
5. The product card: a custom result component. Badges: a custom badge component.
6. Platform behavior such as add to cart, currency or background filters: `plugins.common` or `plugins.<platform>`. `config.platform` registers that platform's plugins, so configure them instead of re-implementing them.

If none of these works, stop and ask. Say what is needed, which steps you tried, and the exact type error that blocks it. Moving to `SnapHybrid` is a further escalation, never a first answer.

## Legal and illegal props: change the approach, not the types

The config types are the contract for what locked mode supports. When `validateTemplatesConfig` rejects a prop, selector or component name, that thing is not supported here. Hiding it from the compiler doesn't make it supported. It makes it unchecked, and it breaks without warning on a later upgrade.

Never do any of these to get a rejected value through:

- **Cast it:** `as any`, `as unknown as X`, `as SnapTemplatesConfig`, `as SnapTemplatesConfigUnlocked`, or a cast on an override or props object.
- **Suppress it:** `@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`, `eslint-disable`.
- **Widen it:** annotate the value as `any`, `object` or any looser type than the one expected, so the check passes.
- **Move it out of reach:** build overrides in another variable or file, where the checks no longer see them. See [index.tsx](#indextsx).
- **Route around it:** get the effect at runtime instead, by writing to `window`, mutating a controller or store, or reaching into Snap's DOM.

The same applies inside components, where a Snap component's prop types are the contract. Pass `controller` through as it arrives: `ResultProps['controller']` is already the union that `OverlayBadge` and the other result-level components accept. Where code needs one controller type, narrow with a type guard in `src/functions/`. Comparing `controller.type` inline doesn't narrow, because the field is typed as the whole enum:

```ts
// src/functions/controllers.ts
export const isSearchController = (controller: ResultProps['controller']): controller is SearchController => controller?.type === 'search';
```

## index.tsx

`index.tsx` holds exactly three things:

1. imports
2. one `validateTemplatesConfig({ ... })` call with the whole config written inline as a single object literal
3. `new SnapTemplates(config)`

**Keep the config literal inline, in one piece.** The `snap-config/validate-config` lint rule only reads an object literal passed straight to `validateTemplatesConfig`, and typed linting is configured for `src/index.tsx` alone. TypeScript's excess-property checks also apply only to fresh literals. Overrides imported from another file let a misspelled prop next to a valid one, and a `resultComponent` naming an unregistered component, pass both `tsc` and `npm run lint`. Written inline, lint flags both.

Plain values stay inline because they are configuration: `siteId`, breakpoints, colors, labels, layout arrays. Everything else lives in its own module and is imported:

| Kind                                                                                             | Home                                                          |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| CSS of any kind                                                                                  | `src/styles.ts`, or `src/styles/*` composed into it           |
| Components and JSX                                                                               | `src/components/`, registered by async import (example below) |
| Functions: override handlers such as `onAddToCartClick`, translation value functions, formatters | `src/functions/`, referenced by name in the config            |
| Types                                                                                            | `src/customTypes.d.ts`                                        |

```ts
components: {
	result: {
		CustomResult: async () => (await import('./components/Result')).CustomResult,
	},
},
```

Type a function against the prop it fills, using the global aliases: `export const handleAddToCart: ResultProps['onAddToCartClick'] = (e, result) => { ... };`.

`index.tsx` has no side effects: no `document.querySelector`, no event listeners, no `MutationObserver` or retry loops, no injected `<style>`. When the storefront itself needs changing, that is theme work. Write it up for the engineer instead of patching it from the bundle.

Delete code rather than commenting it out. Replace the scaffold's commented examples as you configure each section, and don't add new commented-out config.

## Styling

- **All CSS lives in style scripts.** `src/styles.ts` exports `globalStyles: StyleScript`, wired up as `theme: { style: globalStyles }`. No CSS in `index.tsx`, no `style={...}` props in components, no `<style>` elements, no `element.style` writes.
- **Target Snap's `.ss__*` classes** and the class names your own components render. Never select on Emotion-generated class names (`css-1a2b3c`).
- **Native page elements can't be styled from here.** Global styles are scoped under Snap's theme root, so selectors for the storefront's own header search, predictive dropdown or drawers never match. Those changes belong in the site theme: list them for the engineer. Hiding native elements for local preview goes in `public/index.html` only.
- **Use theme variables.** Build media queries from `variables.breakpoints`, never hardcoded pixels, so they stay in sync with the responsive overrides. Read brand colors from `variables.colors` (`primary`, `secondary`, `accent`), set once in `theme.variables`.
- **Return one plain object** from `globalStyles`. The SDK shallow-merges it with `Object.assign`, so an array breaks even though the type allows one.

When `styles.ts` grows, split it into one module per area under `src/styles/`. The spread that combines them is shallow, so two modules that both return the same `@media` key silently drop one of them. Nest media queries inside each selector, and give every top-level selector exactly one owning module. Leave the module's return type inferred, so the spread type-checks and the result is still checked against `StyleScript` in `styles.ts`:

```ts
// src/styles/toolbar.ts
export const toolbarStyles = ({ variables }: Parameters<StyleScript>[0]) => ({
	'.ss__toolbar': {
		gap: '12px',
		[`@media (max-width: ${variables.breakpoints.tablet}px)`]: {
			gap: '8px',
		},
	},
});

// src/styles.ts
import { toolbarStyles } from './styles/toolbar';
import { facetStyles } from './styles/facets';

export const globalStyles: StyleScript = (theme) => ({
	...toolbarStyles(theme),
	...facetStyles(theme),
});
```

## Components

- **Snap component first.** Before writing UI, check `@athoscommerce/snap-preact/components` and the docs. `Price`, `Image`, `Rating`, `OverlayBadge`, `CalloutBadge`, `Carousel`, `Slideshow`, `Swatches` and `VariantSelection` already exist. Never hand-roll sliders, swatch strips, badges or price formatting.
- **Select a custom result** with `resultComponent` on a template (`search`, `autocompleteFixed`, a recommendation template) or with `theme.globalResultComponent`.
- **One card per design.** If autocomplete or recommendation cards differ from the search card, give each its own component (`src/components/ac/`, `src/components/recs/`) instead of branching on `controller.type` inside one card. A ternary may pick a value, such as a class name or a URL. It shouldn't pick between two blocks of markup.
- **Keep components to markup.** Shared logic such as price rules, URL building and attribute parsing goes in `src/functions/`.
- **Props come from the global aliases.** Type a result component as `(props: ResultProps)`. Don't import or redeclare it.
- **Variant-aware cards** read `result.display.mappings.core`, which updates when a variant is selected; `result.mappings.core` doesn't. Wrap any component that reads state changing after the first render in `observer` from `mobx-react-lite`.
- **No manual tracking.** Beacon impression and click tracking is built in. Don't add `controller.track.*` calls, `withTracking` or `ResultTracker`.

## Types

- **No `any`, explicit or implicit.** Because `strict` is off, the compiler won't flag an implicit `any`. Annotate function parameters and empty arrays or objects yourself, and use `unknown` with narrowing when a type is genuinely open.
- **Project types go in `src/customTypes.d.ts`.** They are ambient, so other files use them without importing. Use the slots it provides: `interface Window` for platform and app globals, and `type Result` for feed fields (`attributes`) and values plugins attach at runtime (`custom`). Mark fields optional unless the feed always sends them. Don't declare types in components or in `index.tsx`, and don't create `src/types/`.
- **Reuse the global aliases** from `src/types.d.ts` (`ResultProps`, `SearchController`, `StyleScript`, `ThemeVariables` and others) and derive from them, as in `ResultProps['onAddToCartClick']`, instead of writing parallel types. Extend `Result`, never `ResultProps`.
- **Custom elements** copied from a theme's markup get a real type, never `any`. Add this to `customTypes.d.ts`, above `declare global`:

  ```ts
  declare module 'preact' {
  	namespace JSX {
  		interface IntrinsicElements {
  			'product-block': JSX.HTMLAttributes<HTMLElement>;
  		}
  	}
  }
  ```

- **`import type`** for imports used only as types.

## Gotchas

- Responsive overrides (`mobile`, `tablet`, `desktop`) merge onto `default`; they don't replace it.
- A custom toolbar or sidebar `layout` replaces the default one entirely. Keep `banner.header`, `banner.banner` and `banner.footer` in the toolbars and `banner.left` in the sidebar. Otherwise merchandising banners configured in the Athos console stop rendering, with no error.
- Facets and sort options come from the API. Never hardcode them or trim the list to match a design: style whatever comes back.
- If the search input isn't inside a `<form>`, set `autocomplete.action` to the results page URL, or submitting goes nowhere.
- `config.siteId` decides which index every request hits. A wrong one quietly returns another store's products, so don't change it without confirming.
- Lint enforces only `no-console`, `no-debugger` and the config validator. Everything else on this page is on the author.
